Tasks, v3

C301 (g), redrawn with your notes on v2. A main task is a task: it has a box, like its sub-tasks. A task with no model is yours, so nothing says "yours" or "you"; the only state written is "done", and "running" while a model works. A task is added with a plus: a name, a description if you like, its rooms, its model, which its sub-tasks take unless you change it, and a flow: all at once, or one by one.

"About it" and "207 · run 2 of 2" are gone. The runs stay under the task. The changes to what is stored are in section 5.

1 · The board

Every task, newest first, each with its box. A click on a title opens it under its row; the plus adds one. A task with a model shows the model; one without shows nothing more.

  • A box ticks a task done, as tick: does, said under the bar and taken back by undo:. A task with a model is done when its answer comes; its box ticks then, and ticking it yourself marks it done without sending it.
  • The main task's box ticks itself when every sub-task is done, and ticking it ticks those of its sub-tasks still open that have no model.

3 · Flow

How a task's sub-tasks run, set on the task.

One by oneEach after the one before, in one chat, so each model reads what came before it. A sub-task with no model holds those after it until you tick it.
All at onceAll sent together, each in a chat of its own, reading only its task and itself. A sub-task with no model holds nothing up.
  • run:207 runs a task as its flow says; the Enter line names each model, what it costs and, one by one, where it will wait for you.
  • With a model, the task's own name and description go with each of its sub-tasks, so each knows what it is part of. A task with a model and no sub-tasks is sent as itself: its description, or its name.
  • The flow can change until the task first runs.

5 · What is stored: shown before building

A task stays a plan's record (a docket), with its runs; a sub-task stays a step. They gain the fields the form sets; each is optional, and a record without them reads as now.

A task

{
  id: "d-81…", num: 207,
  title: "Grant application",
  description: "The two-year grant…",
  model: "claude-sonnet-5-5",
  rooms: ["mode_dfe1…"],
  flow: "oneByOne",
  doneAt: null,
  branches: [ … ], order: [ … ]
}

A sub-task

{
  id: "s-7c1e…",
  status: "ready",
  title: "Tighten to a page",
  prompt: "Keep the figures…",
  model: "claude-opus-5-5",
  room: null,
  condition: null
}
  • description up to 4,000 characters; model null for yours; rooms room ids, empty for none; flow "oneByOne" (the default) or "together"; doneAt when the task was ticked, or null. On a sub-task, title up to 200 characters; its model null means it takes the task's, and a sub-task of yours keeps its words in todo, as built.
  • One by one is one branch with the sub-tasks in order, as a plan runs now; all at once is a branch for each sub-task. Both are the stores there are.
  • No migration: no record rewritten, no store, index or version changed. A restore checks each field. Backups carry them; one made before reads as now; an older Parliament drops them and shows the task as a plan.

6 · To rule

  1. The board: every task with its box, one open in place; a plus to add a task and a sub-task; no "About it", no run count at the top; the runs under the open task.
  2. The words on it: no "yours" or "you"; only "done", and "running" while a model works.
  3. The main task's box ticks itself when every sub-task is done; ticking it ticks the open sub-tasks with no model.
  4. Adding: name, description if wanted, rooms by search or list, model (None first, yours), flow; sub-tasks start with the task's model and rooms, each changeable.
  5. Flow: one by one (one chat, in order, waiting for you at yours) or all at once (a chat each, nothing waits); the task's name and description go with each sub-task.
  6. The stored change: description, model, rooms, flow and doneAt on a task, title on a sub-task.
